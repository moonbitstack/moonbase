API Reference

Every public type, function, method and value in moonbase, grouped by package. Signatures come from pkg.generated.mbti; the notes come from the /// doc-comments in the sources.

@moonbase

The positional base-N core, the error types and the streaming engine. Every other package is a table of digits on top of this one.

struct
struct Alphabet

An ordered set of digit characters defining a positional numeral system. The character at index i is the digit of value i, so the first character is always the zero digit. Build one with [Alphabet::new] and hand it to [encode] / [decode]; the base58 and base62 packages are thin wrappers that pin a specific alphabet.

function
fn Alphabet::base(Self) -> Int32

The radix of this alphabet — the number of distinct digits.

function
fn Alphabet::char_of(Self, Int32) -> Char

The character for digit value v, where 0 <= v < base.

function
fn Alphabet::new(String) -> Self raise BadAlphabet

Build an [Alphabet] from its ordered digit characters, e.g. Alphabet::new("0123456789abcdef") for lowercase hexadecimal. Fails rather than aborts: an alphabet often comes from configuration, and a library has no business killing the program over a value it was handed.

function
fn Alphabet::of(String) -> Self

An alphabet written as a literal in source, where a mistake is a programming error rather than bad input. This is the one place the library still aborts: new exists for alphabets that arrive at runtime, and this one for the six that ship with the library and are covered by its tests.

function
fn Alphabet::value_of(Self, Char) -> Int32?

The digit value of c in this alphabet, or None if c is not one of its characters.

error
suberror BadAlphabet
NotAscii(at~ : Int32, char~ : Char)
Repeated(at~ : Int32, char~ : Char)
TooFew(count~ : Int32)

Why an alphabet could not be built. Separate from [Malformed] on purpose: a malformed input is the caller's data, a malformed alphabet is the caller's code.

error
suberror Malformed
Bad(at~ : Int32, char~ : Char)
Truncated(at~ : Int32)
Padding(at~ : Int32)
Checksum(at~ : Int32)

Why a string could not be decoded, and where. Decoding fails for four reasons and each of them names the offending index, because "it did not decode" is not enough to fix a malformed document. The old spelling returned None and said nothing; callers who only want that much can still write try? decode(s).

struct
struct Sink

A streaming encoder: bytes go in a chunk at a time, text comes out as it is produced. The one-shot [encode] needs the whole payload before it starts, which is fine for a token and wrong for a file or a socket. A Sink carries the half-finished character between chunks, so feeding b"foo" then b"bar" gives the same string as feeding b"foobar" — the tests check that against random splits, not just the obvious one. ``moonbit nocheck let sink = @base64.sink() sink.write(b"foo"[:]) sink.write(b"bar"[:]) sink.finish() // "Zm9vYmFy" ` This is the bit-packing engine, so it serves base2, base8, base16, base32, base45, base64 and base85, each of which decides its next character from the next few bits. The positional encodings (base10, base36, base58, base62) have no streaming face at all, and that is a decision rather than an omission: they read the payload as one big-endian integer, so the first digit of the answer depends on the last byte of the input. Nothing could be emitted before the whole payload had arrived, which is what [encode](#encode) already waits for. A face that only ever emitted at finish would add a name, not a capability, so those four take a whole value through encode_big / decode_big`.

function
fn Sink::drain(Self) -> String

Take what has been produced so far and forget it, for a caller writing to a socket who does not want to hold the whole output in memory. The half-finished character stays behind, so the next [write](#write) picks up where this one stopped.

function
fn Sink::finish(Self) -> String

Close the sink: flush the trailing bits, add the padding, and return everything that has not been drained yet. The trailing partial group is shifted up and filled with zero bits, exactly as the one-shot encoder does it. Writing after this call is a mistake with no defined result.

function
fn Sink::new(Int32, Array[Char], Bool) -> Self

A sink that emits one character per bits bits, drawn from digits. padding fills the last group with =, the way RFC 4648 does; the encodings that do not pad pass false.

function
fn Sink::write(Self, BytesView) -> Unit

Feed the next chunk. Nothing is emitted until there are enough bits for a whole character, so a chunk may produce no output at all.

struct
struct Source

A streaming decoder: text goes in a chunk at a time, bytes come out. The mirror of [Sink]. A character may straddle two chunks, so the decoder keeps the bits it cannot yet turn into a byte; and because it remembers how many characters it has seen, a failure found in the third chunk still names the index it would have had if the whole input had arrived at once.

function
fn Source::drain(Self) -> Bytes

Take the bytes decoded so far and forget them.

function
fn Source::finish(Self) -> Bytes raise Malformed

Close the source and return every byte that has not been drained. Fails if the input ends in the middle of a group — a whole character that cannot become a byte — with the same [Truncated](#Truncated) the one-shot decoder raises.

function
fn Source::new(Int32, Array[Int32], Bool) -> Self

A source that reads one character per bits bits out of lookup. lossy skips anything outside the alphabet instead of failing, the way [decode_lossy](#decode_lossy) does.

function
fn Source::write(Self, StringView) -> Unit raise Malformed

Feed the next chunk of text. Fails at the first character that is not in the alphabet, naming the index it has in the whole input rather than in the chunk.

function
fn decode_lossy(StringView, Alphabet) -> Bytes

Decode, skipping anything outside the alphabet. Never fails, which is what a payload wrapped in newlines or punctuation needs. What it cannot do is tell you the input was wrong.

function
fn encode(BytesView, Alphabet) -> String

Encode raw bytes to a string over alphabet. Leading zero bytes map to leading zero-digit characters; the rest is read as a big-endian integer and rewritten in the target base. Round-trips with [decode].

function
fn encode_big(@bigint.BigInt, Alphabet) -> String

Write a whole number of any size in this base. [encode_int](#encode_int) stops at a UInt64, which is where most ids stop too — but a hash, a committee size or a Snowflake-style identifier is wider than that, and a positional encoding has no reason to be. Like encode_int this keeps no leading zeros: a number has none to keep. A sign is not part of any alphabet here, so a negative value is encoded as its magnitude. Ask with value.compare_int(0) first if the sign can vary.

function
fn encode_bytes(BytesView, Alphabet) -> Bytes

The same encoding, as the ASCII bytes it would be written with.

function
fn encode_int(UInt64, Alphabet) -> String

Write a whole number in this base, without the leading-zero rule that the byte-oriented faces keep.

@base58

The Bitcoin, Flickr and Ripple alphabets over the base-N core — 0, O, I and l left out so a string survives being read aloud — and base58check.

Which of the three base58 alphabets is in use. All three leave out the characters a reader confuses — no 0, O, I or l — but they put the rest in a different order, so a string from one is not a string from another. @base85

Adobe's Ascii85, ZeroMQ's Z85 (RFC 32) and the IPv6 spelling of RFC 1924 — four bytes in five characters, three ways.

enum
enum Kind
Ascii85
Z85
Ipv6

Which of the three base85 spellings is in use. Ascii85 is Adobe's: it lives inside PostScript and PDF, writes a group of four zero bytes as a single z, and lets the last group be short. Z85 is ZeroMQ's (RFC 32): the same five-for-four arithmetic over an alphabet safe to put inside a string literal, but with no shortcuts, so the length must be a multiple of four. Ipv6 is RFC 1924's: the input is one 128-bit number, not a run of four-byte groups.

Ascii85 shortens its last group instead, so it encodes whatever it is given.

@bech32

BIP 173's bech32 and BIP 350's bech32m: a human-readable prefix, five-bit groups, and a BCH checksum that the two variants do not share.

struct
struct Decoded

A bech32 string taken apart: the prefix a human reads, and the data a machine reads.

enum
enum Kind
Bech32
Bech32m

Which checksum: the one BIP 173 defined, or the one BIP 350 amended it to. They are the same code with a different constant folded in at the end, so the two families of strings do not overlap: a string that verifies as one never verifies as the other. A witness version-0 output is bech32, everything from version 1 up is bech32m. A format that has never used bech32 at all — a lightning invoice, say — picks bech32m, because the amendment is the one that does not have the insertion weakness.

struct
struct Words

The same, before the five-bit groups have been turned back into bytes. This is the layer the specification actually defines: BIP 173 checksums the five-bit groups, and a string whose data is not a whole number of bytes is a perfectly valid bech32 string — abcdef1qpzry9x8gf2tvdw0s3jn54khce6mua7lmqqqxw is one. Turning the groups into bytes is a separate, stricter step that a checksum verifier has no business doing.

function
fn bytes_of(BytesView) -> Bytes raise @moonbase.Malformed

Five-bit groups back to bytes, strictly. The leftover bits of the last partial byte must be fewer than five and all zero: a decoder that ignores them accepts four different strings for one payload, which is a malleability bug rather than a convenience.

function
fn decode(StringView, kind? : Kind) -> Decoded raise @moonbase.Malformed

Decode a bech32 string to the bytes its data part stands for. Fails if the checksum does not match, if the data does not fill whole bytes, or if the padding that completes the last byte is not zero. A segregated witness address does not fill whole bytes — its first group is a version, not the top of the program — so it fails here with [Padding](#Padding) and belongs in [decode_words](#decode_words). That is a property of addresses; bech32 itself never promised its data would be bytes.

fn decode_words(StringView, kind? : Kind) -> Words raise @moonbase.Malformed

Decode to five-bit groups without turning them into bytes. This is the check BIP 173 specifies: length, character range, one case throughout, a separator, at least six checksum characters, and a checksum that matches the constant of kind.

function
fn encode(StringView, BytesView, kind? : Kind) -> String raise @moonbase.Malformed

Encode bytes as a bech32 string. ``moonbit nocheck @bech32.encode("bc", program) // "bc1q…" @bech32.encode("tb", program, kind=Bech32m) ` The bytes are written as five-bit groups, zero-padded to a whole group, which is the same 1/2/3 to 2/4/5/7/8` expansion base32 does — the difference is that bech32 pads nothing back on the way in and puts a checksum on the end instead. The prefix is written lower case whatever case it arrives in: a bech32 string is either all lower case or all upper case, never both, and the checksum is computed over the lower-case form.
