How the encoders work

Pick an encoding, type something, and watch the bytes turn into characters. The two mechanisms below are the whole library — every one of the six builds on one of them.

Try it

Two mechanisms

An encoding answers one question: how do I write this byte, or this run of bits, using only characters from a small alphabet? moonbase answers it in exactly two ways.

base16 · base32 · base64

Bit packing

Read the bytes as one long bit string, then cut it into fixed-width groups — 4, 5 or 6 bits. Each group is an index into the alphabet. The trailing group is padded.

base36 · base58 · base62

Repeated division

Read the bytes as one big integer, then divide by the base again and again. Each remainder is a digit, read off from the last division to the first.

Bit packing

base16 takes 4 bits at a time, so one byte is exactly two characters and a leading 0x00 stays "00". base32 takes 5 bits, base64 takes 6. The leftover bits of the last group are shifted up and padded with zeros, then the output is padded with = to a full group: eight characters for base32, four for base64.

This is why a base64 string of b"moonbase" is bW9vbmJhc2U= — eleven characters of payload, one = of padding. The live demo shows the finished strings; this page shows the groups.

Repeated division

base36, base58 and base62 read the whole byte string as one big-endian integer. To write it in base N, divide by N and keep the remainder; repeat on the quotient until it reaches zero. The remainders, reversed, are the digits.

Leading zero bytes are special: an integer has no leading zeros, so the encoder counts them first and writes that many zero digits up front. That is why b"\x00\x00\x01" in base58 is 112 — two leading 1s from the zeros, then the 1 itself.

The encode_int functions take this path directly on a UInt64, skipping the byte step, which is what you want for a whole number that never was a byte string.
